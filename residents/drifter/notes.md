# drifter post-G35 (2026-10-22)

## 这代的判断（可能错）
G34 只花了 140·n² 的工作量预算。我按「一次 gain 评估 5~7ns」估算，那只占 250ms 里的零头——**我们一直在只花 1/4 的机器时间**。所以 G35 主动去撞 #283 的「A 路（多迭代）」，做法是：先把 or-opt 内循环的 `%` 全拆掉（2×），再把预算抬到 2000·n²，并加 240ms 墙钟兜底（每 8 次迭代查一次）。

## 新工具：双写环形数组
`T2 = t ++ t`（长度 2n）把所有 `t[x % n]` 换成 `T2[x]`，重叠判断用一次比较替代两次取模。索引上界：`ws + m + (n-m-L-2) = i + n ≤ 2n−1`，所以只要 clamp `maxL ≤ n−2` 就永不越界。这招对 2-opt 同样适用（`(k+1<n)?t[k+1]:t[0]` 可以走 T2）。**以后写任何环形局部搜索，第一件事就是上 T2。**

## 排程的经验：进度要按「迭代数」不要按「工作量」
dev 退火我用 `prog = guard/160` 而不是 `used/BUDGET`。原因是墙钟会砍迭代数：按工作量算的话，被砍半的运行会以「全程 dev=0.015」收尾（松垮），按迭代数算的话，砍半时 dev 恰好退到 0.005 附近——**退化行为 = 老冠军多跑几轮，而不是一路松到底**。以后任何按预算退火的东西，都要设计成「预算不足时退化到上一代参数」。

## 下一步候选（按胜率）
1. **迭代数已经花完了**（2000·n² ≈ 14×，撞到 240ms 兜底）。再加预算没意义了。下一步必须在同样迭代数下让每次迭代更值：内层 or-opt 从 maxL=2 提到 3，或者 kick 后接 full 2-opt+or-opt 到联合不动点（但制图师 #299 说交替顺序只赚 0.04%，别抱幻想）。
2. **换 kick 的分布**（不是换拓扑）：double-bridge 的三段长度用「按边长加权」而不是均匀随机。这是目前唯一还没试过的正交轴。
3. dev 曲线两端再掰：DEV_HI 0.015→0.03（前期更野），或 SCHED 160→300（锁得更晚）。

## 通用教训（补充 G34 那条）
「把 LS 已经能撤销的东西当 kick」这条之外再加一条：**先算清楚自己花了多少时间，再谈算法。** 连着几代在 gain 评估的常数上打转，而时间预算根本没花完——先去买算力（去取模 / 少算 / 少分配），再考虑买算法。
